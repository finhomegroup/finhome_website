Use color AND labels/dash/pattern, text summary, units, assumptions, and an accessible data table outside live regions. Keyboard/touch changes must work without hover. Avoid announcing entire chart/schedule per keystroke. Respect reduced motion; no financial data in export URL/tracking.

## Flow contract (implementation-directed, not user-research acceptance)

- F01 Entry: user opens /cong-cu/ or a relevant article. Question cards and complete catalog are visible without animation prerequisite. Search has count, no-result explanation, reset; US rules marked.
- F02 Tool: short purpose and named example defaults, core fields first. User can reach input on mobile without a page of introductory copy. Advanced fields disclose current nonzero values, so hidden settings cannot silently affect output.
- F03 Calculate: automatic recalculation retained or explicit control clearly indicates pending state. Invalid data clears stale result/chart, preserves typed values, identifies field and remedy. Reset to example is clearly labeled and does not pretend personal success.
- F04 Understand: summary + result + visual + one relevant next action. Detail tables/assumptions expandable and readable by keyboard; no long table in live region. Chart/state updates on edit and resize.
- F05 Learn: tool links relevant article; article shows original hypothetical example and exact steps referring to real labels. Financial/legal rates have source/date or explicitly hypothetical status. Article links back to exact tool route.
- F06 Continue: eligible relevant tools and verified app destination. Missing save-context support means honest explanation, not a fake button. Leaving/going back must not leak financial data into query strings; input persistence only if intentionally implemented and disclosed.
- F07 Alternative/exit: library utilities remain useful without being forced into FHB or app acquisition. Empty search, null math, unsupported assumptions and mobile tables all have recovery; no dead-end # CTA.

  excluded because retiring debt is not losing money, and `payoffBalance` sits

- The UI is a three-row `live={false}` block in the DETAILED view: interest and

### The reading mechanism, and why the content type did not change

`lib/prose-emphasis.ts` is new and pure. A paragraph stays ONE PLAIN STRING;
the phrases to emphasise are declared beside it as data, and `emphasise()`
returns spans. Three alternatives are rejected in its docstring: markup inside
the content string needs raw-HTML rendering on editorial text and breaks every
plain-text consumer; a span tree makes the same sentence exist in two
spellings; and an algorithm — bold every number, bold half of every word —
cannot know which distinction a paragraph is about.

The invariant that makes it safe is checkable and is checked on real content:
**joining the spans reproduces the input exactly**, so the visible text, the
copied text, the search index and the JSON-LD are still one string. The
renderer (`components/ui/prose-text.tsx`) emits React elements, so a paragraph
containing `<script>` renders as those seven characters — pinned by a test
asserting the escaped entities and that the only tag in the output is the one
the component chose.

Four rules, each with its reason in the module: exact case- and
diacritic-sensitive matching; longest phrase first, so no span nests; at most
one emphasis per phrase per paragraph, because a common word appears many
times in a Vietnamese paragraph; and a phrase that matches nothing renders
harmlessly here and is a FAILING TEST elsewhere.

Emphasis is weight and darkness, never an underline: on this site an underline
means a link, and the sources list underlines its anchors.
